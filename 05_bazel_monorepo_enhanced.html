1. Scope and Validation Notes

✅ Main Conclusion

A Bazel monorepo should be designed around explicit ownership, small reusable packages, strict dependency visibility, reproducible external dependencies, and automated query checks that prevent architectural erosion over time.

📖 New to monorepos? Start here

A monorepo (monolithic repository) is a single Git repository that holds the source code for many projects — multiple services, libraries, tools, and tests — all in one place.

Think of it like a shared filing cabinet for an entire engineering organization. Instead of every team having their own private cabinet (separate repos), everyone uses the same one with clearly labelled folders and locked drawers (visibility rules).

The opposite is a polyrepo — one repository per project. Both approaches have trade-offs, and Bazel is specifically designed to make monorepos manageable at scale.

This document targets Bazel 9.1.0, a minor LTS release backward compatible with Bazel 9.0. Examples use @rules_cc for C++ rules. In Bazel 9.x, cc_library, cc_binary, and cc_test must be explicitly loaded — Bazel no longer provides them as built-in rules.

1.1 Lab prerequisites

  • Bazelisk or Bazel 9.1.0 installed — see the Bazel Installation Lab
  • GCC or Clang with C++17 support (g++ --version or clang++ --version)
  • Linux, macOS, or WSL shell
  • Git, tree, jq (optional: Graphviz for dependency graphs)

2. Monorepo Design Principles

A monorepo is a single source repository containing multiple applications, libraries, tools, tests, schemas, and deployment code. It is not merely many projects dumped into one Git repository. The value comes from consistent build rules, shared review policy, unified dependency versions, and safe cross-team refactoring.

💡 Analogy — think of it like a city

Each neighbourhood (package) has its own rules and character. Roads (dependencies) connect them in one direction — cars don't drive backwards on a one-way street. City planners (BUILD files + visibility) decide which roads exist. Breaking a road requires a permit (review).

2.1 Core principles

PrincipleWhat it means for a beginnerHow Bazel enforces it
Small packages Each directory does one thing. A "pricing" directory only holds pricing code — not auth, not logging. One BUILD.bazel file per logical directory. Bazel only rebuilds the smallest affected unit.
Explicit dependencies If your code uses a library, say so in deps. Don't rely on something being available "by accident" because another target pulled it in. Bazel enforces that you can only use what you explicitly list in deps. Missing deps cause build errors, not runtime surprises.
Stable public APIs Don't expose internal implementation files to the whole world. Decide what other teams are allowed to depend on. visibility attribute controls exactly which other packages may depend on a target.
Hermetic builds "Hermetic" means sealed off from hidden influences. The build output should be the same on your laptop, your colleague's laptop, and CI. Pin the Bazel version (.bazelversion), toolchains, and all external deps (MODULE.bazel). No $(shell which python) surprises.
Fast feedback When you change one file, only rebuild and retest what is actually affected — not the entire repository. bazel query rdeps() finds affected targets. Remote cache skips already-built actions. CI sharding runs tests in parallel.

2.2 Recommended enterprise decomposition

enterprise-monorepo/ ├── MODULE.bazel — declares the module name and all external deps (Bzlmod) ├── .bazelversion — pins Bazel version, e.g. "9.1.0" ├── .bazelrc — shared build flags for all developers and CI ├── apps/ — deployable services, CLIs, daemons ├── libs/ — shared C++ libraries used by multiple apps ├── platforms/ — cross-compilation platform definitions ├── tools/ — Starlark macros, code generators, formatters ├── third_party/ — vendored or mirrored external dependencies ├── docs/ — architecture decisions, migration notes └── ci/ — CI pipeline scripts and configurations
⚠️ Rule: libs/ is not a dumping ground

Every shared library must have: an owner (who is responsible for it), an API boundary (what it exposes), tests (that prove it works), and a visibility policy (who can use it). If a library doesn't have these, it becomes legacy code that nobody dares to change.

3. Enterprise Repository Structure

For large organizations, directory structure should quickly answer four questions about any file: Who owns this code? What can depend on it? How is it tested? Can it change without rebuilding everything?

3.1 Annotated structure for C++ services

enterprise-monorepo/ ├── apps/ │ ├── order_service/ │ │ ├── BUILD.bazel — defines cc_binary for the service executable │ │ └── main.cc — entry point; #include from libs/ only │ └── billing_service/ │ ├── BUILD.bazel │ └── main.cc ├── libs/ │ ├── common/ — foundation types used by everyone (Status, Error, etc.) │ │ ├── BUILD.bazel — typically visibility: public (it's truly foundational) │ │ └── status.h — header-only; no .cc needed │ └── pricing/ — business logic for price calculations │ ├── BUILD.bazel — visibility restricted to approved consumers │ ├── price_calculator.h │ ├── price_calculator.cc │ └── price_calculator_test.cc └── tools/ └── build_defs/ — shared .bzl macros to keep BUILD files DRY

3.2 Naming conventions

ItemConventionExampleWhy
Bazel packages (directories) Lowercase, underscores //libs/pricing Consistent across Linux/macOS/Windows file systems
Targets Descriptive noun phrase price_calculator Clear intent when appearing in bazel query output
Test targets Target name + _test price_calculator_test Easily found with kind('cc_test', //...)
Public headers Stable include path from workspace root libs/pricing/price_calculator.h Consumers' #include paths never change when you reorganize internals
Private implementation Same package or internal/ subpackage libs/pricing/internal/ Signals "do not include this directly" to readers

4.2 Shared foundation — libs/common

💡 Why a Status type?

Rather than using exceptions or raw bool return values, a Status type carries both success/failure state AND a human-readable message. This is a common C++ pattern from Google (Abseil's absl::Status). We define a simple version here to keep the example self-contained.

C++libs/common/status.h
#ifndef LIBS_COMMON_STATUS_H_
#define LIBS_COMMON_STATUS_H_
#include <string>
#include <utility>

namespace enterprise::common {

/// Lightweight result type — carries success/failure + message.
class Status {
 public:
  /// Create a successful status.
  static Status Ok() { return Status(true, "OK"); }

  /// Create an error status with a message.
  static Status Error(std::string message) {
    return Status(false, std::move(message));
  }

  bool               ok()      const { return ok_; }
  const std::string& message() const { return message_; }

 private:
  Status(bool ok, std::string message)
      : ok_(ok), message_(std::move(message)) {}
  bool        ok_;
  std::string message_;
};

}  // namespace enterprise::common
#endif  // LIBS_COMMON_STATUS_H_
Bazel BUILDlibs/common/BUILD.bazel
# Load cc_library from rules_cc — required in Bazel 9.x
load("@rules_cc//cc:cc_library.bzl", "cc_library")

# Make all targets in this package publicly visible.
# This is correct for a foundation library used by everyone.
package(default_visibility = ["//visibility:public"])

cc_library(
    name = "status",
    hdrs = ["status.h"],    # header-only library — no srcs needed
)

4.3 Business logic — libs/pricing

C++libs/pricing/price_calculator.h
#ifndef LIBS_PRICING_PRICE_CALCULATOR_H_
#define LIBS_PRICING_PRICE_CALCULATOR_H_
#include "libs/common/status.h"    // include path from workspace root

namespace enterprise::pricing {

/// Returns amount reduced by discount_percent (e.g. 10.0 = 10% off).
double ApplyDiscount(double amount, double discount_percent);

/// Returns Ok() if amount >= 0, Error() otherwise.
enterprise::common::Status ValidateAmount(double amount);

}  // namespace enterprise::pricing
#endif
C++libs/pricing/price_calculator.cc
#include "libs/pricing/price_calculator.h"

namespace enterprise::pricing {

double ApplyDiscount(double amount, double discount_percent) {
  return amount - (amount * discount_percent / 100.0);
}

enterprise::common::Status ValidateAmount(double amount) {
  if (amount < 0)
    return enterprise::common::Status::Error("amount cannot be negative");
  return enterprise::common::Status::Ok();
}

}  // namespace enterprise::pricing
C++libs/pricing/price_calculator_test.cc
#include "libs/pricing/price_calculator.h"
#include <gtest/gtest.h>

namespace enterprise::pricing {

TEST(PriceCalculatorTest, DiscountReducesAmount) {
  EXPECT_DOUBLE_EQ(ApplyDiscount(100.0, 15.0), 85.0);
  EXPECT_DOUBLE_EQ(ApplyDiscount(2500.0, 10.0), 2250.0);
  EXPECT_DOUBLE_EQ(ApplyDiscount(100.0, 0.0), 100.0);  // no discount
}

TEST(PriceCalculatorTest, ValidateRejectsNegative) {
  EXPECT_FALSE(ValidateAmount(-10.0).ok());
  EXPECT_TRUE(ValidateAmount(0.0).ok());
  EXPECT_TRUE(ValidateAmount(5000.0).ok());
}

TEST(PriceCalculatorTest, ErrorMessageIsDescriptive) {
  auto s = ValidateAmount(-1.0);
  EXPECT_FALSE(s.ok());
  EXPECT_FALSE(s.message().empty());
}

}  // namespace enterprise::pricing
Bazel BUILDlibs/pricing/BUILD.bazel
load("@rules_cc//cc:cc_library.bzl", "cc_library")
load("@rules_cc//cc:cc_test.bzl", "cc_test")

# Default: nothing in this package is visible outside unless explicitly allowed.
package(default_visibility = ["//visibility:private"])

cc_library(
    name  = "price_calculator",
    srcs  = ["price_calculator.cc"],
    hdrs  = ["price_calculator.h"],
    deps  = ["//libs/common:status"],  # explicit dep declaration
    visibility = [
        # Only these two packages may depend on this library.
        "//apps/order_service:__pkg__",    # __pkg__ = this package only
        "//apps/billing_service:__pkg__",
        "//libs/pricing:__subpackages__",  # internal test targets
    ],
)

cc_test(
    name    = "price_calculator_test",
    size    = "small",                     # max runtime: 60s
    srcs    = ["price_calculator_test.cc"],
    deps    = [
        ":price_calculator",              # local target (shorthand)
        "@googletest//:gtest_main",        # provides main() for tests
    ],
)

5. Dependency Boundaries

Dependency boundaries are the difference between a healthy monorepo and an unmaintainable folder. Without them, everything gradually becomes coupled to everything else — until no one dares change anything.

Boundary typePurposeExample
Package boundary Separates ownership. Each directory with a BUILD.bazel is a package with a defined owner. //libs/pricing is owned by the Pricing Team
Target boundary Exposes exactly the reusable unit — not the whole directory. //libs/pricing:price_calculator
Visibility boundary Restricts who may take a dependency. Bazel enforces this at build time. //apps/order_service:__pkg__
Ownership boundary Humans enforce this through code review. CODEOWNERS file maps directories to teams. CODEOWNERS: libs/pricing/** @pricing-team
🚫 Dependency rules to enforce
  • App → App forbidden. order_service must never depend on billing_service's internal targets. Extract shared code into a library.
  • Low-level → high-level forbidden. libs/common must not depend on apps/ or business-logic libraries.
  • Test utilities stay in tests. Production cc_library targets must not depend on test helper libraries.
  • Third-party entry points are controlled. Don't allow arbitrary @boost//:boost usage everywhere. Wrap it in a //third_party/boost:headers target with a clear owner.

Query-based policy checks

These queries can run in CI to catch architecture violations before they are merged:

Shell
# Show the dependency path from order_service to pricing (proves they're connected)
bazel query 'somepath(//apps/order_service:order_service, //libs/pricing:price_calculator)'

# Would common accidentally depend on apps? (should print nothing — no path found)
bazel query 'somepath(//libs/common:status, //apps/...)'

# Who currently depends on pricing? (run in CI to detect unauthorized consumers)
bazel query 'rdeps(//..., //libs/pricing:price_calculator)' --output=label

# Check all targets in libs/ package
bazel query '//libs/...'

5b. Visibility — Explained for Beginners

Visibility is Bazel's access-control system for build targets. It answers the question: "Which other packages are allowed to put this target in their deps?"

🌍
Public
//visibility:public
Anyone in the entire workspace can depend on this. Use for true foundation libraries like libs/common.
🔒
Private
//visibility:private
Only targets in the same package (same directory) can depend on this. The default in most packages.
🎯
Package
//apps/svc:__pkg__
Only this specific package may depend on it. Use when you have known consumers you want to approve explicitly.

There are also two more patterns worth knowing:

  • //apps/order_service:__subpackages__ — allows order_service and all subdirectories under it
  • //apps:__subpackages__ — allows any package under apps/ (use for test-only helpers visible to all app tests)
💡 How to read a visibility violation error

If a target has insufficient visibility, Bazel prints:

ERROR: Target '//libs/pricing:price_calculator' is not visible from
       target '//apps/notification_service:notification_service'

This means notification_service tried to depend on price_calculator, but the pricing library's visibility list does not include //apps/notification_service:__pkg__. Either add it to the list (if it's a legitimate consumer) or extract a new shared library.

Package-level defaults vs target-level overrides

You can set a default for the whole package with package(default_visibility = [...]), then override individual targets:

Starlarklibs/pricing/BUILD.bazel
# Package default: nothing visible outside
package(default_visibility = ["//visibility:private"])

cc_library(
    name = "price_calculator",   # overrides the package default
    ...
    visibility = [
        "//apps/order_service:__pkg__",
        "//apps/billing_service:__pkg__",
    ],
)

cc_library(
    name = "internal_helpers",  # inherits private default — no visibility attr needed
    ...
)

6. Large-Scale Repository Management

AreaPracticeWhy it matters
Target granularity Prefer many small cc_library targets over one giant one. Bazel only rebuilds changed targets. One big library means rebuilding everything when any file changes.
Ownership Use a CODEOWNERS file and per-package BUILD.bazel owner comments. Prevents unreviewed cross-team changes from silently breaking downstream consumers.
Performance Use remote cache, local disk cache, and CI test sharding. At scale, a cold build can take hours without caching. A warm cache reduces this to minutes.
Observability Use --profile, bazel aquery, Build Event Protocol. Identifies which actions are slow, which targets are hotspots, and where cache misses occur.
Refactoring Use bazel query before and after large changes. Find all affected targets before merging. Safer than finding out in production.

CI affected-only build strategy

On pull requests, you rarely need to rebuild everything. This strategy builds and tests only what changed:

Shellci/affected_build.sh
#!/bin/bash
set -euo pipefail

# Step 1: find files changed vs main branch
CHANGED_FILES=$(git diff --name-only origin/main...HEAD)
echo "Changed files: $CHANGED_FILES"

# Step 2: convert file paths to Bazel source-file labels
# e.g. libs/pricing/price_calculator.cc → //libs/pricing:price_calculator.cc
FILE_LABELS=$(echo "$CHANGED_FILES" | awk '{
  n=split($0, parts, "/");
  pkg=""
  for(i=1;i<n;i++) pkg=pkg"/"parts[i]
  print "//"substr(pkg,2)":"parts[n]
}')

# Step 3: find all targets that depend on changed files
AFFECTED=$(bazel query \
  "kind('cc_test|cc_binary', rdeps(//..., set($FILE_LABELS)))" \
  --output=label 2>/dev/null || true)

if [ -z "$AFFECTED" ]; then
  echo "No affected targets — skipping build."
  exit 0
fi

# Step 4: build and test only affected targets
bazel test --config=ci $AFFECTED

7. Security and Reproducibility

Bazel's design helps reproducibility, but security requires discipline: pin versions, verify sources, use hermetic toolchains, enable sandboxing, and control cache access.

ControlRecommended practiceWhat happens if you skip it
Bazel version Pin with .bazelversion. Different developers use different Bazel versions → different build behaviours.
External dependencies Use MODULE.bazel lockfiles, approved registries. Unpinned deps can silently upgrade and introduce breaking changes or vulnerabilities.
Toolchains Register explicit compiler versions. Developer A uses GCC 12, CI uses GCC 13 → subtle ABI differences and warning divergence.
Build environment Use --experimental_strict_action_env. Builds leak host environment variables (PATH, HOME) and become non-reproducible.
Remote cache CI writes; developers only read. A compromised developer machine could upload poisoned cache entries that everyone else downloads.

Security-focused .bazelrc — annotated

Bazelrc.bazelrc
# Bzlmod is the default in Bazel 9.1. This line is informational.
# common --enable_bzlmod  ← deprecated flag; remove it to avoid WARNING

# Don't allow host env vars to leak into build actions.
# Makes builds consistent across machines.
build --experimental_strict_action_env

# Stricter version of the above — enables it for all spawn strategies.
build --incompatible_strict_action_env

# When debugging: shows sandbox directory structure and keeps it after failure.
# Remove in production (slow).
# build --sandbox_debug

# Print which .bazelrc flags are active — helps diagnose "why is this flag set?"
build --announce_rc

# ── Remote cache configuration (CI vs dev separation) ─────────────
# Only CI writes to shared cache; developers read only.
# Uncomment and configure for your infrastructure:
# build:ci  --remote_cache=https://cache.example.com
# build:ci  --remote_upload_local_results=true   # CI writes
# build:dev --remote_upload_local_results=false  # devs read only
🚫 Remote cache poisoning — what it is and why it matters

Cache poisoning means an attacker uploads a malicious build artifact (compiled binary) to a shared remote cache. Other developers and CI pipelines then download and use that artifact without rebuilding from source — unknowingly running the attacker's code.

Prevention: never let arbitrary developer machines write to the shared CI cache. Only trusted, authenticated CI runners should write. Everyone else reads. Authenticate cache access with TLS client certificates or signed tokens.

8. Common Pitfalls and How to Fix Them

Pitfall 1: Making everything public

The most common beginner mistake. Using //visibility:public everywhere feels convenient — no visibility errors — but destroys architectural discipline over time.

❌ Bad — everything public
package(default_visibility =
  ["//visibility:public"])

cc_library(
    name = "internal_helpers",
    srcs = ["internal.cc"],
    # now anyone can depend
    # on internal impl details
)
✅ Good — private by default
package(default_visibility =
  ["//visibility:private"])

cc_library(
    name = "internal_helpers",
    srcs = ["internal.cc"],
    # private: only targets in
    # this package can use it
)

Pitfall 2: One giant common library

Putting all shared code in a single cc_library means changing one file rebuilds everything that depends on it — potentially the entire monorepo.

❌ Bad — monolithic common
cc_library(
    name = "common",
    srcs = [
        "status.cc",
        "logger.cc",
        "config.cc",
        "http_client.cc",
        "db_connection.cc",
    ],
    # change db_connection.cc
    # → rebuild everything
)
✅ Good — split by capability
cc_library(name = "status",
  hdrs = ["status.h"])

cc_library(name = "logger",
  srcs = ["logger.cc"],
  deps = [":status"])

cc_library(name = "http_client",
  srcs = ["http_client.cc"])
# each target rebuilt
# only when IT changes

Pitfall 3: Depending on transitive headers

Just because //libs/pricing depends on //libs/common:status doesn't mean you can #include "libs/common/status.h" in your code without adding //libs/common:status to your own deps. If pricing ever removes that dependency, your build breaks.

⚠️ Rule: declare every direct dependency explicitly

If your .cc file has an #include, the included library must appear in your target's deps, not just in a transitive dep's deps.

Pitfall 4: Unpinned external dependencies

Without pinning, running bazel build today and tomorrow can produce different binaries because a transitive dep was updated.

❌ Bad — no pinning
bazel_dep(
    name = "googletest",
    # no version specified
    # → gets "latest"
    # → non-reproducible
)
✅ Good — pinned version
bazel_dep(
    name = "googletest",
    version = "1.17.0.bcr.2",
    # exact BCR version
    # → reproducible builds
    # → lockfile tracks it
)

Pitfall 5: Big-bang migration

Attempting to convert an entire large repository to Bazel in one step is very high risk. One broken dependency can block everyone.

✅ Recommended approach: incremental migration
  1. Start with the leaf libraries (no internal dependencies) — they're easy to convert in isolation.
  2. Run Bazel and the legacy build in parallel for a period — compare outputs.
  3. Add a non-blocking CI lane for Bazel before making it the required gate.
  4. Promote to required gate only after two clean release cycles.
  5. Decommission the old build system last.

Required defaults checklist

  • Use BUILD.bazel (not BUILD) for all new packages
  • Use MODULE.bazel with pinned dep versions for all Bazel 9.1 projects
  • Pin Bazel version with .bazelversion in every workspace root
  • Set package(default_visibility = ["//visibility:private"]) in new packages
  • Prefer small cc_library targets (one logical concern per target)
  • Every production library has a corresponding cc_test
  • Load all C++ rules from @rules_cc — never rely on built-in native rules in Bazel 9.x
  • Run CI query checks to prevent architecture violations on every PR

9. Migration Strategy for Existing Enterprise Projects

Migration should always be incremental. A large Make/CMake repository can take weeks or months to migrate safely — and that's fine. The goal is zero disruption to delivery, not a perfect Bazel monorepo on day one.

PhaseGoalOutputRisk level
1. Inventory Understand what exists: apps, libraries, generated code, tests, third-party deps. Migration spreadsheet and dependency map 🟢 Low
2. Pilot package Convert one low-risk leaf C++ library to Bazel — the smallest one with no internal dependencies. First cc_library and cc_test 🟢 Low
3. Build bridge Run Bazel and the legacy build side by side. Compare outputs. Don't break delivery. Parallel CI lane (non-blocking) 🟡 Medium
4. Boundary enforcement Add visibility rules and CODEOWNERS. Establish which packages are public APIs. Architecture guardrails in BUILD files 🟡 Medium
5. External dep migration Move all third-party deps to Bzlmod with pinned versions. Remove inline vendoring. MODULE.bazel and lockfile 🟡 Medium
6. CI adoption Promote Bazel CI lane to required gate. Enable affected-only builds on PRs. Fast monorepo CI pipeline 🟠 Higher
7. Decommission legacy Remove the old build system definitions. Bazel is now the single source of truth. Clean repo, one build system 🟠 Higher

Migration decision matrix

Project typeMigration approachNotes
Small independent C++ library ✅ Migrate first — ideal pilot No internal deps = isolated risk
Business service with many dependencies Migrate after all its internal libraries are converted Bottom-up order prevents broken deps
Generated protobuf/API code Design Bazel generator rules before mass migration Need rules_proto and toolchains first
Security-sensitive component Migrate with strict reproducibility + extra review gates Verify hash/digest of all external deps
Legacy component with unclear ownership Assign an owner and write tests first, then migrate Don't migrate orphaned code — it becomes Bazel orphaned code

}

enterprise::common::Status ValidateAmount(double amount) {

    return enterprise::common::Status::Error("amount cannot be negative");

cat > libs/pricing/price_calculator_test.cc <<'EOF'
#include "libs/pricing/price_calculator.h"
#include <gtest/gtest.h>

namespace enterprise::pricing {

TEST(PriceCalculatorTest, DiscountReducesAmount) {
  EXPECT_DOUBLE_EQ(ApplyDiscount(100.0, 15.0), 85.0);
  EXPECT_DOUBLE_EQ(ApplyDiscount(2500.0, 10.0), 2250.0);
}

TEST(PriceCalculatorTest, ValidateRejectsNegative) {
  EXPECT_FALSE(ValidateAmount(-10.0).ok());
  EXPECT_TRUE(ValidateAmount(0.0).ok());
}

}  // namespace enterprise::pricing
EOF

12. Review and Assessment Questions

Questions

  1. Why is a monorepo not automatically better than multiple repositories?
  2. What problem does Bazel visibility solve?
  3. Why should common libraries be split into smaller targets rather than one big target?
  4. What is the risk of setting default_visibility = ["//visibility:public"] on all packages?
  5. How can bazel query help enforce architecture before a change is merged?
  6. Why should external dependencies be pinned with exact versions?
  7. What is the safest first component to migrate from Make/CMake to Bazel, and why?
  8. Why should the legacy build system and Bazel coexist temporarily during migration?
  9. What is remote cache poisoning and how do you prevent it?
  10. How can CI run only the tests affected by a pull request rather than the whole suite?

Answer key

  1. A monorepo requires governance, ownership rules, tooling, and explicit boundaries. Without these, it becomes a large unmaintainable folder — which is worse than separate repos.
  2. Visibility controls which packages may take a dependency on a target. It separates public API targets from implementation details and prevents unauthorized coupling.
  3. Smaller targets reduce rebuild scope. When target A changes, only targets that directly depend on A are rebuilt — not unrelated targets in the same large library.
  4. It creates uncontrolled coupling. Anyone can add any dependency at any time, making refactoring risky and ownership unclear. Architecture erodes silently.
  5. Use rdeps() to find who depends on a target being changed. Use somepath() to verify no forbidden dependency paths exist. Run these checks in CI on every PR.
  6. Pinning ensures the same artifact is used on every machine and at every point in time. Unpinned deps can silently upgrade, introducing bugs, breaking changes, or security vulnerabilities.
  7. A small library with no internal dependencies — a "leaf" in the dependency graph. It can be converted in isolation without affecting any other component.
  8. It reduces delivery risk. Running both systems in parallel lets you compare outputs and catch differences before Bazel becomes the required gate. It also means developers can keep shipping while migration is in progress.
  9. Cache poisoning is when a malicious or corrupted build artifact is uploaded to a shared remote cache and distributed to other builders. Prevention: only trusted CI runners write to the shared cache; developers get read-only access.
  10. Use git diff to find changed files, convert file paths to Bazel labels, then use bazel query rdeps(//..., set(...)) to find all targets that transitively depend on those files. Build and test only that set.
